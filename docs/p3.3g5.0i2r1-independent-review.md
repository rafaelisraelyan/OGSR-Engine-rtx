## 3. Blocking source finding F1 — `m_intro->Stop(); xr_delete(m_intro)`

R1 patch adds:

```cpp
if (m_intro)
{
    m_intro->Stop();
    xr_delete(m_intro);
}
```

**Existing `CUISequencer` semantics on the exact baseline source:**

1. `CUISequencer::Stop()` calls `Destroy()` normally, but if `m_flags.test(etsPlayEachItem)` and there are entries, it calls `Next()` then **returns without `Destroy()`**.
2. `CUISequencer::Destroy()` removes `this` from `Device.seqFrame/seqRender`, deletes items/UI, calls `m_on_destroy_event()`, then continues checking `g_tutorial == this` / `g_tutorial2 == this`.
3. `CGamePersistent::update_game_loaded()` and `update_logo_intro()` (possible destroy callbacks) call `xr_delete(m_intro)`. In `update_game_loaded()`, it also calls `start_game_intro()`.
4. **Raw R1 log shows `intro_delete ::update_game_loaded` three times, exactly at disconnect/quit**, demonstrating that at least one callback-delete path is exercised by the submitted successful run.

**Why this matters:** `Stop()` can synchronously invoke a callback which deletes the `CUISequencer` *while `Stop/Destroy` are still on its call stack* (re-entrant object destruction); after returning, the outer `xr_delete(m_intro)` may be a no-op if it was nulled, or may delete an object that a callback replaced. In `etsPlayEachItem` mode, `Stop()` can skip `Destroy()`; outer deletion can then leave stale Device callbacks or input capture. The three no-crash runs do not prove either branch safe. **This is an independently source-supported potential lifetime bug introduced by R1; it is NOT a demonstrated new crash.**

**Required closure:** establish a **single owner and single destruction path** for `m_intro` during disconnect. Prevent re-entrant destruction callbacks from deleting the active sequencer during its member function; guarantee removal from seqFrame/seqRender and proper input release regardless of `etsPlayEachItem`, item count and intro variant (logo, game_loaded, intro_game). Preserve the necessary existing side effects of normal completion callbacks when doing an explicit disconnect, without accidental new intro creation. Write targeted test instrumentation and negative tests that confirm: destructor exactly once, callback behavior as specified, Device registrations zero before delete, no callback on freed pointer, and `m_intro==nullptr` after disconnect. Do not replace with a superficial null guard.
