## 3. R1-B live-2: reproducible hang boundary, not proven PhysX teardown failure

`logs/s2r1/reload-teardown2.log` primary evidence:
- At 13:01:22: `S2R1: ragdolls ready live=2 scene_alive=1 scene=(0,1) lease_refs=3 dll=1`.
- At 13:01:32: `S2R1: queue disconnect`.
- At 13:01:32.701: `ph_runtime: v2 teardown state: remaining=0 live=0 lease_refs=1`, then `v2 scene destroyed; lease_refs=0`.
- At 13:01:33.745: both `ph_ragdoll: releasing PhysX owner state` messages appear, one per NPC.
- `S2R1_TEARDOWN: begin`, `after pLevel`, `after level_Unload`, `after cameras`, `after seq remove`, `after resetpp`, `after sound`, `after g_pGameLevel null`, finally **`after hud` at 13:01:34.376**, after which the **file ends**. No `S2R1: level down` / `queue level start` / `KERNEL:start` event.
- Developer reports process alive with ~80 seconds CPU and ~1.3GB WS, no fatal/AV; raw artifact shows the logging boundary **but not thread stacks, actual hang-site instruction or CPU thread**.
- `logs/s2r1/reload-no-ragdoll.log` with same PhysX feature flags but no live V2 instances has 2 ready levels/2 disconnect and clean exit. Strong controlled correlation with **live ragdoll lifetime**, not sufficient to pinpoint code location or conclude the PhysX SDK hangs.
- Earlier `reload.log` is a **separate inconclusive attempt**: it logs timeout waiting for two ragdolls, then normal quit; only `reload-teardown2.log` proves live=2 immediately before disconnect.

**Critical boundary correction:** The test-only `IGame_Level::~IGame_Level` patch logs `after hud` immediately after `xr_delete(g_hud)` but **before** the conditional `B2CameraCapture_OnLevelTeardownComplete()` and destructor return. Therefore its presence does **not literally prove return from the destructor**. Missing markers after `xr_delete(g_pGameLevel)` in `CApplication::OnEvent(eDisconnect)` leave several possible sites:
1. Last optional level teardown callbacks / actual destructor return.
2. `Console->Show()`.
3. Conditional `Console->Execute("main_menu on")`, dependent on pending `KERNEL:start/quit`.
4. `g_pGamePersistent->Disconnect()` (forced intro cleanup, ambient particles, spatial DB clear, sound stop).
5. Deferred EventAPI/Device frame continuation and new `KERNEL:start`, including test-only callback lifetime.

The actual production source `ogsr_engine/xr_3da/x_ray.cpp::CApplication::OnEvent` confirms this order: `net_Stop` → `xr_delete(g_pGameLevel)` → `Console->Show` → conditional menu on → `g_pGamePersistent->Disconnect()`. The event is processed from `CEventAPI::OnFrame`, which maintains an event queue and dispatches callbacks. No evidence currently singles out any one of these as the culprit.

**Do NOT treat `lease_refs=0` as proof that no CPU-side deadlock, stale callback, or UI/event ordering bug exists.** It proves PhysX scene/DLL lease teardown recorded successful completion.

### NEW F1 — incomplete test harness source provenance

The provided `patches/g51-s2r1-test-harness.patch` is **UTF-16LE**, not a directly applicable UTF-8 Git patch. It includes a new `xrGame.vcxproj` compile item `ogsr_s2r1_harness.cpp` and external calls `OgsrS2R1HarnessRegister()` / `OgsrS2R1HarnessUnregister()` in `x_ray.cpp`. **The patch contains no `diff --git` entry for that C++ implementation**, and the ZIP has no standalone `ogsr_s2r1_harness.cpp`. The missing file is likely central to the test mode that queues reload, making this more than cosmetic provenance. Reviewer verified that the three relevant **production** files `x_ray.cpp`, `ogsr_physx_ragdoll.cpp`, `ogsr_physx_runtime.cpp` contain no such definitions at the pinned source. The test harness is **not reproducible from the submitted test-only patch**; its callback implementation and potential role in the hang **cannot be audited**. Preserve this as a new **EVIDENCE BLOCKER**, not a proven bug in production PhysX.

The test-only patch also changes `XR_3DA.vcxproj` `WholeProgramOptimization` and `/LTCG:OFF` for instrumentation; do not infer exact production perf from instrumented EXEs without acknowledging this difference. It includes unrelated UI test hooks; keep all of them out of normal `prypiat`.

## 5. R1-C: independent recalculation from six raw CSV files

Each `csv/perf-*.csv` contains **2401 parsed data rows**: `measure_start` sentinel, 2399 intermediate entries, `measure_end` sentinel (advertised 2400-frame measurement window). Independently recomputed p50, p95, p99 and CPU physics duration using the bundled script's `floor(p·(N−1))` percentile convention, confirming reported summaries:

|---|---:|---:|---:|---:|---:|
| ODE-1 | **49.3870** | 0 | 0 | 0 | **24** |
| ODE-2 | **33.4660** | 0 | 0 | 0 | 0 |
| ODE-3 | **33.4718** | 0 | 0 | 0 | 0 |
| PhysX-1 | **33.4894** | **0.3591** | **0.5898** | 0.8017 | 0 |
| PhysX-2 | **33.4412** | **0.3840** | **0.6778** | 1.0041 | 0 |
| PhysX-3 | **60.8378** | **0.5364** | **1.0845** | **35.1611** | **217** |

- Median of run-level frame p99: **PhysX 33.4894 ms vs ODE 33.4718 ms**, difference **+0.0176 ms**. However this **does not eliminate** the severe third PhysX run. Its frame time exceeds 50ms in **217 of 2401 samples**, versus ODE-1 with **24** outlier frames.
- The largest PhysX-3 **frame** spikes (100.0/91.04/87.0 ms) were accompanied by ordinary PhysX step ~0.5ms, so *those specific frames* cannot be explained by the recorded PhysX step alone.
- **NEW F2 perf caution:** Other PhysX-3 samples independently record **individual PhysX CPU step durations ~35.1611, 32.7122 and 31.6157 ms**. Therefore a blanket statement that *all* PhysX-3 stalls are unrelated to physics is unsupported; these long steps require mapping to V2 SceneStep, synchronization, scheduler/preemption, logging or measurement error. The current per-run CPU p99 is small, but tail/worst-case is nontrivial.
- User's `nofpslock`/vsync-off setup still yielded ~33ms frames for most runs, so this is **render/pacing constrained behavior**, not proof of uncapped GPU potential or production performance ceilings. The current **test-only build disables LTCG/WPO**, another reason not to infer production FPS from these numbers.
- **R1-C evidence/sample reproducibility PASS**, but **performance-stability interpretation CONDITIONAL**, especially before increasing concurrent ragdolls to 4/8/16.
