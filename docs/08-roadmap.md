# OGSR RTX — дорожная карта

> **Актуализировано: 21 ноября 2026.** Основная ветка: `prypiat`.  
> Это **план развития**, а не журнал ежедневных отчётов и проверок. История прежних решений доступна [в старой версии roadmap](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/blob/521cde4e685d003a7ee8f4e0cf08a2730fb45ab8/docs/08-roadmap.md).

## Цель

Дать OGSR / X-Ray современный рендерер DirectX 12, сохранив игровой мир *S.T.A.L.K.E.R.: Call of Pripyat*, его геометрию, логику, атмосферу и существующий DirectX 11 / R4. Затем — выборочный аппаратный DXR, современные материалы, объёмную погоду и оптимизацию открытых уровней.

Главный критерий прогресса — **видимый и работающий результат в самой игре**, а не один красивый кадр отдельного теста.

Ревью предоставленных кадров/логов **PASS WITH NOTES**, исходников — **PENDING** | Подтвердить код/сборку и исправить оставшиеся игровые пропуски |

## 1. Ближайший приоритет — сохранить всю накопленную работу

**Сначала коммиты и публикация существующего DX12-кода, потом дальнейший F4.2.**

- Кодовый базис F4.0-B: локальный `81956aa1a`. Последний заявленный F4.1-E: `5c26e8442`, ветка `feature/f41-full-static-jupiter`; ключевые предыдущие коммиты `a2cfaec18` и `de1d2661f`.
- На момент сверки эта feature-ветка **ещё не найдена на GitHub**. Требуется сохранить историю F4.0-B → F4.1-E с обычным push, без squash/force-push и без загрузки игровых архивов/бинарников.
- После публикации: независимая проверка исходников, итогового Git tree, одной чистой сборки и адресных R4/DX12 smoke. В старых F4.1-тестах R4 загружал Jupiter и Zaton, но **штатное завершение процесса с кодом 0 не доказано** — [#7](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/7).
- **Кодовая публикация ≠ merge.** Перенос DX12 в `prypiat` возможен только с отдельного разрешения владельца и после ревью.

### Что доказано для F4.1-E

| Jupiter / текущая статическая сцена | Результат по предоставленным evidence |
|:--|:--|
| Секторов / visual ID в `level` | 151 / 20 880 |
| R4 vs DX12, IDs и типы | **20 880 / 20 880**, несовпадений 0 |
| Подготовленных рисуемых статических visuals | **13 911** |
| Структурных записей без собственного draw | **6 969**: `MT_HIERARHY` + `MT_LOD` |
| GPU-пулы | 36 VB / 11 IB, около 93,8 МБ |
| Запрошенные DDS-текстуры | 365 загружено, неподдержанных 0 |
| Проверенные DX12 GPU прогоны | Debug Layer / GBV без ошибок |

Исправлены автором и подтверждены логами пропуски `MT_TREE_PM` (таблица SWI находится в `level.geom`) и дочерних visuals `MT_LOD` (теперь обходятся все дети); `dropped_unreachable=0`. Это **охват статического контейнера**, а не полная отрисовка игрового мира. [Сравнение R4 и DX12 — #10](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/10).

Оставшиеся видимые различия имеют другую природу: двери создаются как игровые `CPhysicObject` / `MT_SKELETON_RIGID` через `Render->model_Create`, а растительные детали поступают отдельно из `level.details`. Они **не входят** в 20 880 visuals контейнера `level`. Кроме того, не хватает правильного alpha-blended отображения воды/стекла. [Двери — #9](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/9), [материалы — #6](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/6).

Доказательства: предоставленный владельцем `F4.1E-Comparison-Report.md`, сопоставленные R4↔DX12 снимки и архив `OGSR-F4.1-screenshots-and-reports-20261121-141641.zip`. Их целостность проверена, но они не заменяют ревью кода и новый запуск Windows.

## 2. DX12 — ближайшие функциональные этапы

| Порядок | Этап и результат | Критерий готовности |
|:--|:--|:--|
| **Сейчас** | **F4.1-E — публикация и контроль кода** | Доступная feature-ветка, сохранённая история, независимый source review, короткий R4/DX12 regression |
| **Следующий** | **F4.2-A — игровые rigid skeletal visuals**: настоящие двери, лампы, ящики, динамические world/bone transforms | Те же объекты на своих местах из той же игровой камеры R4/DX12; корректный creation/destruction и GPU lifetime — [#11](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/11) |
| **Следующий** | **F4.2-B — `level.details`**: трава, мелкие элементы, инстансы по данным `CDetailManager` | Корректная плотность/расположение, видимость, память, реальные R4-сравнения — [#12](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/12) |
| **Затем** | **F4.3 — материалы, небо, базовый свет**: opaque/cutout/blend, нормали, солнце, первые тени | Убраны грубые материальные дефекты; сцена воспринимается как игровая, а не как unlit-превью |
| **Затем** | **F4.4 — полная динамическая сцена**: NPC и анимация, оружие, HUD и необходимые render passes | Нормальный игровой эпизод на Jupiter/Zaton в DX12 с реальными игровыми объектами |
| **Перед интеграцией** | **F4.5 — lifecycle и устойчивость**: смена уровня, `vid_restart`, minimize/restore/resize, device loss, долгий gameplay | Обоснованные GPU/RAM бюджеты, отсутствие UAF/GBV ошибок, чистый выход, DX11/R4 regression |
| **Позже** | **F5 — temporal и апскейлинг**: motion vectors, TAA/DLSS/FSR при готовом кадровом контракте | Стабильность в движении, history reset, измеренные GPU ms и задержки |

**Способ работы:** не возвращаться к ручным whitelist из пяти объектов и не писать второй параллельный VFS loader. Использовать общие `level.geom` GPU-пулы, существующий `gr::jobs::JobSystem` и game-owned DX12 device/queue/frame. Динамика передаётся через immutable snapshots; GPU buffers/descriptors освобождаются только после нужных fences. Параллельную GPU-запись включать только при доказанном выигрыше, не ради самого числа workers.

**Ранние условия приёмки:** разные позиции игровой камеры, сопоставимые R4-кадры, счётчики loaded/reachable/visible/drawn/unsupported, Debug Layer/GBV, нормальный exit. Наличие отдельных кадров с нулём GPU errors не доказывает корректность level reload или device loss.

## 3. DXR / RTX — гибридный рендеринг

Сначала пригодный игровой DX12 raster; затем выборочное аппаратное RT по принципу полезности, а не попытка сразу заменить весь кадр path tracing. *Control* — ориентир гибридной интеграции, большие открытые сцены S.T.A.L.K.E.R. требуют своей стратегии.

| Очередь | Что создаём |
|:--|:--|
| **G0** | Проверка DXR tier, fallback на устройствах без RT, DXC/SDK и бюджета |
| **G1** | Обычные BLAS/TLAS из настоящей геометрии X-Ray, resource lifetime и обновления |
| **G2** | Первый проверенный RayQuery/DispatchRays с согласованными geometry/material IDs |
| **G3** | **RT-тени** в игровом кадре с raster fallback, замерами качества и GPU ms |
| **G4** | Dynamic geometry, skinned actors и alpha-tested vegetation в структурах лучей |
| **G5** | RT-отражения; при отдельном решении — ограниченная GI и denoise |

**PBR** развивается параллельно: новые физические материалы не должны ломать старые игровые DDS/THM. Полная PBR-конверсия не является обязательным условием первых RT-теней. **CLAS/Cluster BLAS и PTLAS** — необязательные будущие эксперименты **после** обычного BLAS/TLAS; преимуществ пока не доказано. [Официальные DX12/DXR reference](09-dx12-port-references.md).

## 4. Объёмные облака и погода — самостоятельный трек V

Художественная цель — объёмные облачные массы с глубиной, внутренним светом и погодными переходами, сохраняющие стиль Зоны. **Original V-SF Rain** — сохранённый контроль дождевых облаков; зрелый грозовой фронт **не принят**. [Визуальный ориентир](dx12-v-cloud-visual-target.md) и [морфология облаков](dx12-v-scientific-cloud-taxonomy-and-transitions.md).

| Порядок | Текущий статус |
|:--|:--|
| **V-WEATHER-01C-B — ближайшее** | В rebuilt R4 от 21.11 независимый Codex нашёл **2×P2, REQUEST CHANGES**: блокирующее логирование при GPU кадрах in-flight и недоказанная корректность stdout/stderr fault-controls. **R4-R1 — узкое исправление, текущий gate HOLD** |
| **01C-C — затем** | GPU profiling по профилям/погоде/разрешениям и выбранный safe default. **NOT RUN** |
| **V1/V2 — качество** | Standalone ray marcher существует, но **V1/V2 formal PASS ещё нет**. Спорные морфологические HCS1/HCS2 не переносить в shader до R03A read-only review |
| **V-Q4 — игровой композитинг** | Подключить проверенный cloud pass к существующему игровому DX12. Хотя game-owned device/Present уже есть в F4.1, HDR sky/color/depth, weather snapshot и композитинг пока не подтверждены; **не интегрировано** |
| **V-L / V-S — дальние задачи** | Молнии, единая погодная система и эффекты выброса после базовой игровой интеграции |

**Инварианты:** в игре один renderer/device/queue/frame owner и один GR Job System; облака — GPU ray marching, а не самостоятельный runtime. `CEnvironment` задаёт погоду и время. Обычный игрок меняет качество облаков (Classic 2D / опциональные 3D), но не seed, density или сценарии грозы; developer override не должен попадать в shipping Release. Нужен безопасный классический fallback. Сами облака не блокируют F4.2.

## 5. PhysX — экспериментальный ragdoll при сохранённом ODE

**В `prypiat` уже слит PhysX-код через [PR #1](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/pull/1)**. Это source integration, не разрешение включать PhysX по умолчанию: обычное движение/AI — ODE, opt-in ragdoll — отдельный эксперимент, ODE остаётся fallback.

В контролируемом тесте **16 одновременно активных человеческих ragdolls** и 17-й ODE fallback подтверждены с оговорками. **Нормальный массовый gameplay, сохранения, контакты, performance и разнообразие rigs не приняты.**

**Ближайший шаг — G5.1-S3R-R2, исследование без новой production-функциональности:**

1. Найти источник неожиданного `GE_DESTROY` после загрузки сохранения; сопоставить судьбу трупа и инвентаря при PhysX on/off на одном сейве.
2. Снять синхронные трассы CPU/worker/GPU и выяснить причину длинных кадров и dropped physics steps.
3. Проверить dense/empty/boundary static collisions, кэширование и lifetime при выгрузке и повторном входе.

**Статус R2 — AUTHORIZED / NOT RUN. Full G5.1 — HOLD.** [Текущее задание и критерии](p3.3g5.1-s3r-r2-targeted-followup.md). Дальше — реальный save/load/level reload, длительный gameplay, разные человеческие rigs, loot, стабильность, измеренные бюджеты и независимое ревью.

Автоподгонка PhysX под разные скелеты, мутанты, массы NPC/экипировки и портируемый адаптер IX-Ray — **долгосрочные идеи, не принятая функциональность**. [PhysX architecture ADR](physics-portability-adr.md).

## 6. Другие идеи — не блокируют текущий DX12

| Направление | Статус / дальнейшее решение |
|:--|:--|
| **DLSS SDK** | Обновление до **310.9.1** выполнено и исторически проверено в CoP. Поддерживать, не повторять этап A |
| **NVIDIA Image Scaling на DX11** | Подготовка скрипта/submodule сделана, compute/UI integration не готова. Отдельный backlog |
| **DLSS quality flags** | Alpha/jitter/sharpening проверять по SDK и реальным кадрам, не включать вслепую |
| **DX11 Hi-Z / SSGI** | Исследовательский план, **отложен** в пользу полноценного DX12; не путать screen-space GI с DXR |
| **CI / техдолг** | Локальные исправления по реальным блокерам, не массовая косметическая чистка |
| **Общая многопоточность X-Ray (H)** | Только после CPU/GPU profiling; существующий GR foundation не означает завершённую оптимизацию AI/физики |
| **World partition / streaming (I)** | После стабильного DX12 и доказанных IO/VRAM bottlenecks |
| **Visibility / vegetation LOD / тени (J)** | После полного отображения сцены, проверенных culling/LOD и бюджета |
| **Seamless World (K)** | Долгосрочная концепция; не обещать бесшовную A-Life или старые моды без отдельного проекта |
| **Переносимый DX12/DXR / IX-Ray (L)** | Возможное сотрудничество, **не согласовано**, модуль не готов |
| **VFX / аномалии** | Сначала обычные огонь, дым, вода, частицы и переносимый fallback; потом аномалии |
| **Audio** | Только исследование после игрового CPU/аудиопрофиля; OpenAL пока не заменять |

## 7. Правила работы и приёмки

- **Результат важнее отчёта.** Крупные пакеты функций, реальные игровые кадры и измеряемая корректность. Субагентам — ограниченные аудиты, fixtures и анализ; главному исполнителю — архитектура и интеграция.
- **Без бесконечных гейтов.** При checkpoint — быстрые адресные smoke, при завершении пакета — одна соответствующая Windows/gameplay/GR/ASan/Debug Layer/GBV матрица и независимое ревью. Критические memory/ownership ошибки устраняются немедленно.
- **Не смешивать уровни доказательства.** `PLANNED`, `IN PROGRESS`, `EVIDENCE PASS`, `SOURCE REVIEW PENDING` и `PRODUCTION MERGED` обозначают разные состояния. Агентский PASS не является независимой приёмкой.
- **Безопасный DX11/R4 и ODE fallback.** Рендер, физика и gameplay имеют разные границы владения. Новые функции opt-in до принятия, без слепой замены проверенного пути.
- **Git:** сохранять логические коммиты, не переписывать чужие ветки, не делать production merge без отдельного согласия владельца. Docs-only правки не являются разрешением сливать код.
- **Баги:** вести в [GitHub Issues](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues) с симптомом, воспроизведением и доказательствами; не копировать каждый лог в roadmap. Открытые исторические расследования: [#2 — R4 startup AV](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/2), [#3 — DX12 shutdown AV](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/3).
- **Ресурсы:** игровые данные CoP нужны для runtime тестов, но не должны попадать в публичные бинарные/evidence-поставки без прав.
- **Метрики:** число загруженных ресурсов ≠ реальный draw/culling coverage; отдельный GPU timestamp ≠ FPS всей игры.
