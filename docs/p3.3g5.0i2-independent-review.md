### F1 — UI patch residual raw queue risk (targeted test, not proven regression)

In current `UIDialogHolder.cpp`, `CleanInternals()` clears `m_input_receivers` and `m_dialogsToRender` but does **not** clear `m_dialogsToRender_new`. `RemoveDialogToRender` searches only the primary queue; `AddDialogToRender` can place dialogs into the pending queue while `m_b_in_update`. `DestroyInternal` clears only if `m_startDialog->GetHolder()` is non-null. The observed fixed run has `new=0`, so **no stale pending entry is proven**, but acceptance must test an Update-triggered dialog destruction/reload and ensure no stale deferred `CUIWindow*` survives. Do not blindly clear/modify vector during an active iterator traversal; establish safe deferred ownership semantics first.

### F2 — Tutorial reload crash confirmed, «pre-existing» label unproven

In `dumps/harness-load.mdmp`, exception `0xC0000005`, **read at address `0x20`** and `RAX=0` at `CUISequenceSimpleItem::Update+0x168`, `UIGameTutorialSimpleItem.cpp:208`. This source line calls `smart_cast<CUIGameSP*>(CurrentGameUI())`; `CurrentGameUI()` uses `HUD().GetGameUI()`. A temporary/missing HUD/UI during level transition is a **plausible hypothesis**, **not established root cause**. Check actual faulting instruction and CurrentGameUI/HUD state with matching symbols.

**Important harness confound:** crash occurred immediately after `Console->Execute("load g5i1_station")` invoked *inside* a temporary `pureFrame::OnFrame` callback (`G5.0-I2-UI-TestHarness.patch`). This may cause reentrancy/timing effects. Require reproduction by ordinary menu, external/interactive console input, or a proven-safe queued event outside frame callback, on the same baseline and save, before calling the crash pre-existing or making a production fix. `disconnect` crash in earlier harness run at `CGamePersistent::OnFrame` is a distinct confirmed null-level access. **Do not conflate the two crashes.**
