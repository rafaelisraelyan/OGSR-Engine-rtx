# G5.1-S3R-R1 — независимое ревью Codex

11.11.2026, MSK. Строгий READ-ONLY аудит source pin и предоставленного evidence; игра, тесты, компиляция и старые испытания на 16 NPC повторно не запускались. Принятие этапов и решение о production — за Tech Lead и владельцем.

## Executive summary и вердикты

- **R1-A — REQUEST CHANGES.** Непосредственный механизм аварии `g51_s3r_16` доказан: некорректный graph ID используется как индекс при регистрации объекта. Независимо открыты два minidump и найденный вне ZIP полный dump. Отдельно обнаружена потеря обычного corpse ID 13357 после загрузки; происхождение `GE_DESTROY` не установлено, корректное восстановление corpse остаётся открытым.
- **R1-B — REQUEST CHANGES.** Новая методика и все шесть коротких CSV подтверждают наблюдаемые интервалы и снижение частоты больших задержек в этих запусках. Они не объясняют прежний `perf-on-3`, не атрибутируют длинные кадры конкретным потокам и не устанавливают production budget.
- **R1-C — PASS WITH NOTES для узкого расследования и контролируемого 11/11.** Журналы и NPC CSV подтверждают один выбранный ALife-сценарий, 11 PhysX-owned объектов и причину исходного fallback на dense tile. **Production proposal — HOLD**: стоимость и корректность покрытия на разных участках, ресурсный бюджет и длительный lifecycle не доказаны.
- **Общий вердикт: G5.1-S3R-R1 REQUEST CHANGES. G5.1 PRODUCTION GAMEPLAY READINESS — HOLD.** Ранее принятый узкий 16-live gate не пересматривается. Ни одно из этих решений не разрешает merge proposal или default-on.

Наиболее важные уточнения к авторскому отчёту:

1. Отладочные crash-запуски on/off используют разные **варианты бинарника**, однако ни в одном нет флагов включения PhysX ragdoll; минидампы не содержат PhysX DLL. Они убедительно показывают воспроизводимость аварии без активированного PhysX на пути загрузки, но не являются сравнением активной PhysX-сцены с отключённой.
2. Для corpse `13357` финальный on-прогон загружает `g51_s3r_corpse_r1`, а off-прогон — другой `g51_s3r_existing_r1`. Ранее есть on/off загрузки **одного имени** `g51_s3r_existing_r1` с аналогичной последовательностью. Логи ранних on-запусков не закрепляют hash запущенного бинарника и hash save непосредственно на момент каждого прогона. Этого достаточно для сильного ограничения гипотезы PhysX-only, но не для доказательства полного отсутствия влияния PhysX при всех условиях.
3. На найденном полном дампе напрямую получены ID **13847**, `graph=0xffff`, `node=0xffffffff`, `online=false`, `flags=0x21`. Этот dump **не включён в ZIP**, но доступен локально и его SHA-256 проверен; два final minidump подтверждают `0xffff` и стек, но не содержат всех полей объекта.
4. Тест R1-C использует обычные существующие игровые NPC, но контролируемые synthetic hit и test-only настройки. Среди 11 объектов лишь **три visual path**; screenshot слишком тёмный и не показывает 11 проверяемых поз/контактов.

## 2. R1-A: crash и ALife persistence

### Авария local-spawn save — ROOT CAUSE PROVEN для непосредственного сбоя

Оба ZIP minidump прочитаны независимым `minidump_inventory.py`: сигнатура `MDMP`, по 15 записей directory (11 непустых), 117 модулей, исключение `0xC0000005`; имена модулей указывают соответственно `bin_r1_on/xrEngine.exe` и `bin_r1_off/xrEngine.exe`. CDB с локальными matching PDB и без symbol server открыл оба файла (`run_dump.py`, `independent-cdb-on.txt`, `independent-cdb-off.txt`): в обоих `CALifeStorageManager::load → CALifeSimulatorBase::register_object → CALifeGraphRegistry::update → add → CSafeMapIterator::add`, при исключении регистр `r13=0xffff`. Символизированный стек воспроизводит смысл CDB-текстов автора; часть object memory в minidumps недоступна.

Полный dump `C:\OGSR_G51S3R_R1\artifacts\g51-s3r-r1\dumps\r1a-on-g51s3r16-full.dmp` **не был приложен в ZIP**, но найден локально. Его размер **4931421416** и независимо вычисленный SHA-256 **53AFA5A0D32E8E8D94226675338BBB220631796BE497A5EBCB7F279F3D3CB4E8** совпадают с пакетом. Он открыт CDB (`run_full_dump.py`, `independent-cdb-full.txt`): object ID `0x3617` = **13847**, graph `0xffff`, node `0xffffffff`, offline, flags `0x21`; аргумент функции тоже `0xffff`. Full dump относится к **другому, более раннему** `bin_g51_s3r` EXE, а не к final on/off R1 EXE; локальные старые EXE/PDB имеют matching GUID `2DF133C2-CF6E-45DC-A7EE-FEB9D4A7B677` age 6. CDB выдаёт предупреждение о невозможности проверить нулевой PE checksum; привязка по PDB/module ID и данным всё же видна. Не переносить поля этого полного дампа на обе финальные аварии как непосредственно прочитанные.

В source pin `alife_graph_registry.cpp:36,155–166` размер `m_objects` равен числу graph vertices; для offline `used_ai_locations` код выполняет `VERIFY(valid_vertex_id)` и затем индексирует `m_objects[game_vertex_id]`. `xrCore/xrDebug_macros.h:55` делает `VERIFY` пустым при отсутствии `DEBUG`. Full dump плюс source и два независимых final стека подтверждают выход по невалидному graph ID как непосредственный механизм именно этого сбоя; это не доказательство, что любой некорректный save или любой runtime crash имеет ту же причину.

Сохранение `01-r1a/saves/g51_s3r_16.scop` пересчитано: `DBDF94E76ED55FFA9BF154F34D4BD7BD96447915444DA61B3A587C10FEB48BA5`; одноимённый файл runtime **сейчас** имеет тот же hash. CDB logs обоих final запусков называют `g51_s3r_16`, но это не криптографическая фиксация save bytes на момент каждого запуска. В обоих нет `-physx_all_humans` и других флагов opt-in; минидампы не содержат PhysX DLL. Следовательно, корректная классификация — **две сборки, авария без активной PhysX-сцены**, а не доказанный A/B с запущенной PhysX.

`r1a-graphdiag-on.log:8584–8585` отдельно показывает для ID 13847 graph 65535, node 4294967295, offline/used_ai=1 и пропуск guard; 207 сообщений `R1A_GRAPH_INVALID` не означают 207 доказанных crash-объектов: guard пропускает любой invalid graph до проверки исходных условий offline/used_ai. Helper из патча создаёт локальный spawn без явной установки graph ID; связь invalid ID с ним сильно поддержана полями, флагами, именем и соответствующим созданным NPC, но конкретный момент возникновения неверного ID не трассирован. Для arbitrary production ALife saves защиту Release от invalid graph считать непроверенной, а наличие такой ошибки у обычных корректных объектов не утверждать.

### Finding A1 — P1, обычный corpse не восстановлен

**Evidence:** `01-r1a/runs/r1a-corpse-save-final/r1a-corpse-save-final.log:9677,9935,10061–10062,10158` — существующий `sim_default_bandit_1` ID 13357 имеет PhysX owner/shell=null перед запросом save и сериализуется. `r1a-corpse-load-final.log:423,8534–8600,9108–9112,9138,9188`: тот же ID прочитан, зарегистрирован, при frame 31 обработан `server_destroy`, затем `release_begin → unregister → on_destroy_object`, после чего client spawn пропущен как `m_just_destroyed`, и ID отсутствует в post-load registry. Результат — **не подтверждена передача PhysX corpse в ODE**, а не успех persistence.

On/off сравнение: `r1a-existing-load-lifecycle.log:145,421,9111,9140,9191` и `r1a-existing-load-off.log:145,423,9109,9139,9189` оба загружают `g51_s3r_existing_r1` и показывают те же стадии; архив содержит save hash `AD9C0B99C891AC2E5B316C4BF66AFBE5BD58FC3538D0180C23E498E8BF37C3D1`. Финальный `corpse-load-final` использует другой `g51_s3r_corpse_r1` hash `C2713A5675FCB8519680C39D454055BD2E2F7E00EE36EFDD7C70B9DD6DFD21FC`. В обоих сценариях диагностический graph guard включён; ранние on/off логи сами не закрепляют hash файла на момент воспроизведения. Это указывает на общий путь ALife/network, но не доказывает, что ошибка полностью независима от истории сохранения и изменённого harness.

`r1a-living-save.log:9206` и `r1a-living-load.log:423,9119,9133` подтверждают сохранение и post-load наличие живого ID 13357, graph 22 и online=1. Контроль не проверяет dead-body persistence.

**Техническая причина пока не установлена.** `xrServer_process_event.cpp:101–102` направляет `GE_DESTROY` в `Process_event_destroy`; `xrServer_process_event_destroy.cpp` делает ALife release и `Level().OnDestroyObject`, а `Level_network_spawn.cpp:38–43` пропускает ID в `m_just_destroyed`. Это место обработки, не доказанный отправитель или свидетельство, что событие находилось в очереди до save. Не установлены инициатор, возраст event, выбор dead/online и роль графового guard. **Минимальное действие:** инструментировать создание/очередь/доставку `GE_DESTROY` с ID, временем, стеком, источником и состоянием объекта; повторить одинаковые save bytes on/off с зафиксированными hash и guard-off контролем, затем доказать сохранение именно этого corpse и inventory. Не предписывать конкретный фикс до обнаружения отправителя.

### Что измерено и что не измерено

`r1-test-normalized.patch:2015–2024,3100–3120`: `raw_frame_ms` — `steady_clock` между входами harness `OnFrame`, после сброса в `StartPerf`; это полезный CPU-side frame interval, не GPU latency и не гарантированно интервал между дисплейными present. `Device.fTimeDeltaRealMS` — отдельное измерение с разрешением таймера движка; `Device.fTimeDelta` сглажено/ограничено, не raw. `begin_ms` и `present_ms` — стеночное время соответствующих обёрнутых вызовов, не полная GPU duration. `ode_step_ms` и `physx_step_ms` — wall вокруг вызовов; `physx_step_cpu_ms` — оценка циклов вызывающего потока с калибровкой, не сумма PhysX workers.

`worker_cpu_ms=max(0, ΔGetProcessTimes−ΔGetThreadTimes(current))` (`r1-test-normalized.patch:3170–3205`) содержит **все** остальные потоки процесса. Счётчики имеют видимое квантование 15,625 мс, измеряются последовательными системными вызовами, а отрицательные разности обрезаются до нуля; суммарное CPU нескольких потоков вправе превышать wall интервал. Необязательно считать это переполнением: `worker_cpu_ms > raw_frame_ms` встречается примерно в 1021–1046 из 2400 строк каждого run. Отрицательных/неfinite значений CSV нет, но проверка только выходных значений не исключает скрытого overflow и рассогласования интервалов.

Все 7 кадров `raw >50` в шести окнах имеют non-main 46,875–78,125 мс; это ограниченное совпадение, не атрибуция причин. `worker` p99 во многих целых прогонах сам достигает 62,5–93,75 мс, следовательно большие process-minus-main значения не уникальны для long frames. В on-1 frame 2681 raw 52,768 / present 5,261 / SceneStep 0,407 / 1 drop; on-2 frame 1808 raw 64,166 / present 0,110 / SceneStep 0,496 / 2 drops; on-3 frame 2587 raw 78,967 / present 0,098 / SceneStep 0,448 / 3 drops. Смещение границ опросов и квантование не позволяют из этих строк исключить scheduler, worker, GPU/driver, другие виды ожидания, logging или вызов solver в соседнем интервале. Самые большие измеренные вызовы SceneStep недостаточны, чтобы **одни** объяснить длинные кадры.

`Layers/PhysicsPhysX/src/physx_ragdoll_scene.cpp:673–714`: сцена ограничивает delta до 0,25 с, accumulator до `fixed*maxSubsteps*2`, выполняет не больше `maxSubsteps` и отбрасывает остаток целых fixed ticks; runtime задаёт `fixed=0,01 с`, `maxSubsteps=4`. ### Source-level оценка proposal

`ogsr_physx_runtime.cpp:1046–1114` делает `BoxQuery` с margin и назначает triangles tile по centroid; плотность исходного query и count принадлежащих tile различаются. `:1411–1530` проверяет число уже занятых tiles, собирает временные vectors, применяет per-tile и total budget до `sceneAddStaticFragment`; отказ возвращает false и вызывает ODE fallback в обычном activation path. `:1532–1568` требует все клетки вокруг позиции в пределах safety margin. Если предыдущие клетки добавлены успешно, а последующая отвергнута, предыдущие additions остаются в scene/cache: отказ отдельного NPC не означает откат всего набора. Существование этих fragments само по себе не доказывает двойной solver, но потребляет бюджет.

Пустая область или zero centroid-owned triangles возвращает false, даже если отсутствие геометрии является корректным состоянием. Это безопасный отказ по текущему контракту, но может лишать PhysX на пустых ячейках; не следует превращать empty в pass без определения «пустая и достоверно покрытая» и проверки границ. Centroid ownership при ограниченном query/margin не является автоматическим доказательством отсутствия дыр для больших пересекающих границы треугольников; нужны targeted boundary/contact tests с фактической геометрией.

Успешные tiles кэшируются до сброса scene; negative cache и eviction в проверенном пути нет. Повторно запрошенный отвергнутый tile обрабатывается заново: baseline log `r1c2-on-tile96-true.log:794,823` показывает одну и ту же плотную ячейку с extraction 12,05 и 9,94 мс. На большом уровне возрастающие области достигают `max fragments/total` и новые ragdolls переходят на ODE. Это bounded по числу и треугольникам, но **не byte budget** для входного `BoxQuery`, выделений/cooking PhysX, других сцен или промежуточных копий; лимит per-tile 131072 допускает уже около **6 MiB** только для 9 float координат и 3 uint32 индексов на каждый сохранённый triangle, до избыточной capacity, query buffer, конверсий и cooked mesh. Это оценка временных сырых массивов одного полного tile, не измеренный persistent расход и не верхняя граница процесса.

В `Layers/PhysicsPhysX/src/physx_ragdoll_scene.cpp:532–560` fragment готовится до замены, изменение запрещено при `stepping`, а teardown `:320–336` освобождает actor/mesh и очищает registry; интеграция `clearStaticTiles` обнуляет map/counters. Проверенный конкретный запуск логирует release/lease0. Проверка `stepping` сама по себе не является синхронизацией доступа к `g_v2_static_tiles`: потоковая дисциплина и безопасность позднего создания/teardown при других call paths не установлены этим ревью. Доказательств UAF нет, как и полной гарантии его отсутствия на долгом gameplay.

### Finding C1 — P1, производственное расширение лимитов не подтверждено

**Evidence:** три константы proposal; `r1c3-...log:794,2167,3273–3275`; tile extraction и cache source выше. 11/11 устраняет наблюдавшийся cap в выбранной сцене, но синхронные десятки мс, временные allocations и ограниченная выборка не доказывают приемлемый resource budget. **Решение:** не интегрировать proposal без отдельных согласованных многолокационных и длительных тестов: dense/empty/boundary и repeated rejects; worst/p95/p99 extraction/cook, peak и steady memory с OS/allocator attribution; полный cache и ODE fallback; teardown/reload и контакты при активных соседних ragdolls. Простое повышение лимитов может быть временно допустимо лишь после количественно согласованных бюджетов на целевой машине и этих negative/lifecycle проверок. Альтернатива — bounded региональный cache с корректной фиксацией покрытия, ограничением bytes/time и учётом активных ragdolls; rejected/empty cache требует invalidation по generation и отдельного доказательства корректности. Реализация не входит в данный аудит.
