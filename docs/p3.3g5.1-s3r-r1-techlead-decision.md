## R1-A: narrowed root cause accepted; production ALife persistence still unresolved

- **PASS WITH NOTES for direct invalid-graph crash mechanism in the specific local-spawn save:** two final minidumps plus an older, locally found full dump and source analysis establish `CALifeGraphRegistry::add` indexing `m_objects[0xffff]` when `VERIFY(valid_vertex_id)` is compiled out in Release; the full dump identifies object **13847**, offline graph=0xffff, node=0xffffffff. The **older full dump has a different EXE**; do not claim its full object fields were read from each final mini dump. Test-only local spawn without explicit graph IDs is the supported source of invalid test data, not proof of a normal-save PhysX production defect.
- **Both final crash runs omit PhysX opt-in flags** and no PhysX DLL appears in the dumps. They prove the crash in **two different binary variants while PhysX is inactive**, **not** a paired active-PhysX-vs-ODE behavioral equivalence test.
- **P1 unresolved ordinary ALife corpse persistence:** PhysX-owned, then saved existing NPC **13357** is post-load registered but receives `GE_DESTROY` (delivery `server_destroy`), then `release/unregister`, after which `m_just_destroyed` skips respawn; no successful PhysX corpse→ODE restoration or corpse inventory continuity proved. Similar feature-off behavior occurs, but some on/off saves differ and historical launch hashes weren't pinned, so a universal "unrelated to PhysX" conclusion is not independently established. Actual `GE_DESTROY` **sender and enqueue time are unknown**. Diagnostic graph guard alters behavior; no guard bypass is an accepted production fix.
- **Gate:** **R1-A REQUEST CHANGES.** Independently accept specific crash mechanism and observed corpse-destruction timeline only. Require targeted on/off same-save hash controls, opt-in evidence, `GE_DESTROY` enqueue/source stack, and a true corpse+inventory save/load proof before broad G5.1.

## R1-B: measurement corrected; cause not diagnosed

- Codex independently recalculated six short 2,400-sample raw `OnFrame` intervals: ODE 3 mean values **7.550/7.790/7.966 ms**, PhysX 3 **7.757/8.017/8.125 ms**, measured raw >50ms **2 ODE vs 5 PhysX**, dropped PhysX ticks **1/4/3 = 8** within PhysX windows. These are **instrumented CPU-side OnFrame intervals**, not display frame or GPU latency; `Device.fTimeDelta` is smoothed.
- Reported `PhysX SceneStep p99 <0.5ms` for every run is **incorrect**: third PhysX run p99 **0.6789ms** (max **1.0743ms**). Direct SceneStep cost is still too small to account alone for ~79ms frame, but possible indirect waits/workers/render effects are **not isolated**.
- `worker_cpu_ms=GetProcessTimes - GetThreadTimes(main)` counts all non-main process threads; 15.625ms sampling quantization and negative-clamping prevent thread-specific attribution. No ETW/WPA, actual culprit stack, fully optimized WPO/LTCG-on Release budget, or reproduced explanation of previous 178 dropped PhysX steps in `perf-on-3`. Former cumulative 542 spans multiple phases; these R1 short windows do not prove elimination.
- **Gate:** **R1-B REQUEST CHANGES.** Accept narrowed raw-measurement methodology/statistics with notes; keep long-frame/drop root cause and production performance HOLD.

- **Independent narrow PASS WITH NOTES:** controlled synthetic hits on **11 existing `CAI_Stalker` ALife IDs** (only **3** actual visual paths) produce **11 concurrent PhysX-owned bodies**, zero ODE/double-ownership at checkpoint with test-only environment budget override. Successful override uses **max fragments 16, per-tile 131,072, total 262,144**; 9 fragments and **116,295 cached static triangles**, successful `sceneAddStaticFragment` cooking wall sum **74.00ms**, largest tile **46.17ms cook + 14.16ms extraction = 60.33ms**. One run's summed working set changes **~36.52 MiB** are *not* a persistent heap cap or guaranteed peak. Teardown `lease_refs=0` supported for that run.
- Production proposal only changes limits **8→16 / 65,536→262,144 / 16,384→131,072**, and it was **not compiled or executed as a standalone production patch**. Persistent cache has **no eviction or rejected/empty tile negative cache**; multiple successful tile inserts can remain even when later tile fails (no rollback), source query/centroid ownership at borders needs contact coverage tests, and dense cooking is synchronous. Broader worst/p95/p99 memory/time, boundary/empty/rejected scenarios, multiple game regions and extended level unload/lifecycle not validated.
- Screenshot is too dark to independently verify ragdoll poses or contacts; 11/11 evidence rests on registered IDs, log/counters and test-only instrumentation, not independent video.
- **Gate:** **R1-C PASS WITH NOTES for ONE controlled 11/11 static-capture proof; constant-only PRODUCTION PATCH BLOCKED/HOLD**. Require [small focused resource and lifecycle follow-up](p3.3g5.1-s3r-r2-targeted-followup.md) before any production design recommendation.
