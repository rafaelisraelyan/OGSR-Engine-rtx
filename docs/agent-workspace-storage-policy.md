# Политика рабочих каталогов и хранения артефактов агентов

Статус: **проект для внедрения**, 10.11.2026. После утверждения политика обязательна для Codex, OpenCode и любых клиентов, использующих DeepSeek, а также для других агентов проекта. До подключения к их инструкциям наличие этого документа само по себе не гарантирует, что агент его прочитает. Указания пользователя и применимые инструкции среды имеют приоритет; при конфликте требований к изоляции, сохранности или тестированию остановиться и уточнить безопасный способ работы.

Цель — ограничить ненужное расходование места на C: и D:, сохраняя независимость ревью, воспроизводимость и доказательства DX12/DXR и PhysX. Политика распространяется на новые задачи и новые запуски; она не разрешает перенос, изменение или очистку существующих результатов.

## 1. Выбор рабочего окружения

1. До создания копии проверить текущую задачу, `git worktree list --porcelain` и известные подходящие окружения. Для кандидата проверить назначение, владельца, commit, ветку или detached HEAD, `git status`, включая staged и untracked, а также необходимые ignored-файлы, локальные зависимости и результаты. Чистый Git status не доказывает отсутствие ценных ignored-файлов, stash или активного использования.
2. Согласовать с владельцем статус задачи и использование каталога; проверить активные процессы и доступные сведения о занятости. Список процессов сам по себе не доказывает, что каталог свободен. При неизвестном владельце, состоянии или конфликте задач считать окружение занятым до выяснения. Рабочий каталог другого активного агента без согласования не использовать.
3. Повторно использовать совместимое окружение только если это не затрагивает чужие несохранённые изменения, baseline, результаты или независимость проверки. Никаких reset, checkout, пересборки или перезаписи чужих данных для «освобождения» окружения. Для повторного анализа одного и того же задания не создавать worktree автоматически.
4. Отдельная изоляция обязательна, если её требуют пользователь, инструкции, тест, воспроизводимость или контроль независимости. Для независимого ревью при необходимости использовать свежую изолированную копию; повторное использование допустимо только после проверки его совместимости с конкретными критериями независимости. Экономия места не отменяет обязательные проверки.
5. Если новая копия обоснована, до создания записать в манифест задачи её путь, назначение, владельца/агента, исходный полный commit, критерий завершения, причину отказа от повторного использования и предполагаемое размещение сборки. Запись об окончании задачи не даёт права на удаление. Если места или ясности недостаточно, остановиться и сообщить пользователю.

Запись `prunable` в Git не подтверждает безопасность удаления. Не выполнять `git worktree prune`, `remove`, `git clean`, `reset` или аналогичные действия на основании этой политики. Существующие worktree не переподключать и не удалять без отдельного согласованного решения по конкретным путям.

## 2. Каталоги сборки

Создавать новый каталог сборки только при технической необходимости, в том числе для необходимой изоляции. Перед использованием или созданием:

1. Найти доступный совместимый каталог и выяснить его владельца, назначение и занятость. Один каталог нельзя одновременно использовать нескольким агентам без заранее подтверждённой безопасной синхронизации всех читателей и писателей. При сомнении считать его занятым.
2. Сверить исходный commit и локальные изменения, toolchain и его версию, архитектуру, генератор, конфигурацию, флаги, SDK и зависимости. Для CMake дополнительно сверить исходный и build-пути и соответствующие параметры `CMakeCache.txt`; для Visual Studio/MSBuild — solution, platform, configuration, toolset, SDK и пути промежуточных/выходных файлов. Инкрементальную пересборку после смены commit допускать только при подтверждённой совместимости и если результат не требуется сохранить как baseline; зафиксировать фактическое состояние. При несовместимости или неизвестной истории не смешивать конфигурации и не заявлять совместимость.
3. Проверить, не является ли каталог baseline, частью открытого дефекта или доказательством другого теста. Не перезаписывать его. Отдельные сборки CPU/GPU, ASan, Debug/Release, DX11/DX12/DXR или PhysX допустимы, когда этого требует конфигурация или независимость; причину записать.
4. Выполнить оценку места по разделу 4, включая системные временные и выходные каталоги на других дисках. Для каждого запуска зафиксировать реальный путь, идентичность исходников и конфигурацию.

Существующие скрипты могут писать по фиксированным путям или использовать `%TEMP%`. До запуска изучить их фактические выходы, в том числе побочные; задать отдельные пути через поддерживаемые параметры, если возможно. Если изоляция или сохранность не обеспечиваются, не запускать до согласования безопасного способа. Политика не предполагает автоматического изменения скриптов.

## 3. Артефакты и манифест

Для новой задачи использовать логическую структуру `artifacts/<task-id>/`; идентификатор должен быть стабильным и отличаться от других задач. Внутри рекомендуется выделять `reports/`, `logs/`, `metrics/`, `screenshots/`, `evidence/` и отдельный каталог `runs/<run-id>/` или другие уникальные имена запусков, чтобы результаты не перезаписывались. Создавать только необходимые разделы. Каталог артефактов можно расположить на согласованном диске: записать абсолютный путь и доступность; проверить ignore-правила и не предполагать, что он отслеживается Git. Не переносить старые данные ради соответствия схеме.

Для каждого значимого запуска — сборки, теста, независимого ревью, измерения или операции, создающей доказательства, — до начала создать минимальный манифест, затем дополнить его по завершении или остановке. Допустим Markdown, JSON или иной читаемый формат; каждый такой запуск должен иметь свою запись:

```text
Task ID / Run ID:
Агент и владелец:
Дата и время запуска с часовым поясом:
Рабочий каталог / worktree, полный commit и ветка или detached HEAD:
Локальные изменения исходников и их сохраняемое расположение либо «нет»:
Цель, критерий завершения и причина изоляции или повторного использования:
Build path, конфигурация, toolchain/SDK, архитектура, флаги и зависимости:
Команды и параметры воспроизведения, включая пути вывода:
Среда теста при необходимости: GPU, драйвер, ОС, режим validation, сцена и настройки:
Результаты: PASS / FAIL / BLOCKED / SKIP / NOT RUN, ограничения и ссылки на логи:
Уникальные доказательства и baseline: пути, при необходимости хэши:
Статус хранения: Permanent / Active / Regenerable / Unknown; владелец и дата пересмотра:
```

Для короткой READ-ONLY операции без сборки, теста, независимого ревью, измерения и создания доказательств допускается компактная запись в отчёте задачи или журнале сессии без отдельного файла и каталога: цель, агент, дата, commit и существенные локальные изменения, выполненные действия и результат или ограничение. Не относящиеся к операции поля полного манифеста не требуются. Если операция становится значимым запуском или создаёт доказательства, применить полный манифест, сохранив все необходимые сведения и результаты.

Commit не описывает незакоммиченные изменения: указать их происхождение и доступное сохранённое состояние, не выдавая запуск за воспроизводимый, если его восстановление не подтверждено. Для сбоев или прерываний сохранить частичный результат и причину. Сборка не является доказательством успешного runtime, GPU validation или производительности. Уникальные скриншоты, captures, метрики и crash dumps, необходимые для результата, не исключать ради экономии; результаты хранить так, чтобы их можно было найти и проверить. Не создавать гигантские дубликаты исходников в evidence: ссылаться на commit и доступные локальные изменения, а уникальные данные сохранять отдельно. Если ссылка не обеспечивает доступность или воспроизводимость, сохранить необходимый минимальный материал и указать ограничение.

## 4. Бюджет места

Перед крупной сборкой, созданием копии и GPU-тестом проверить доступное свободное место на **каждом** затрагиваемом томе: исходники, build/output, артефакты, `%TEMP%`/`%TMP%`, системный диск и иные известные выходы инструмента. Записать время проверки, тома и свободный объём, ожидаемый расход и основание оценки. Оценивать пик, а не только конечный размер: промежуточные файлы компиляции и линковки, PDB, shader cache, captures, дампы, логи, архивирование и возможные повторные прогоны. Использовать измерения аналогичных запусков, если они есть; при неопределённости явно расширить оценку или остановиться.

Отдельно учитывать необходимый резерв для Windows и других работающих программ, а также уже запланированные параллельные операции. Согласовать владение и планируемый расход с активными задачами; проверка свободного места не резервирует его и может устареть. Перед затратным этапом проверить повторно и контролировать место во время продолжительных запусков. Оценка и резерв определяются конкретной задачей и ситуацией, без универсальной фиксированной квоты или автоматического обрыва теста.

Если оценка вместе с резервом не помещается, либо её нельзя надёжно сделать, подготовку новой сборки или GPU-прогона прекратить. Предложить совместимое повторное использование, другой согласованный том или отдельную проверенную очистку. Не урезать молча обязательные доказательства и не запускать задачу в расчёте на автоматическое удаление. При неожиданном исчерпании места остановить дальнейшие операции безопасным для процесса способом, сохранить доступные результаты и явно пометить запуск неполным.

## 5. Хранение и пересмотр

- **Permanent** — принятые архитектурные решения, важные исходники, roadmap и ADR, уникальные доказательства, эталонные метрики и визуальные сравнения. Сохранять доступность и связь с результатом.
- **Active** — рабочие файлы текущих исследований, GPU captures, crash dumps открытых дефектов, незавершённые сборки и тесты. Не трогать до завершения работы и решения владельца; нужное для дальнейшей проверки может перейти в Permanent.
- **Regenerable** — только подтверждённые промежуточные сборочные файлы, проверенные повторяемые кэши и доказанные точные дубликаты. Совпадение хэша подтверждает содержимое, но не отсутствие зависимостей, владения, жёстких ссылок или активного использования.
- **Unknown** — файлы и каталоги с неизвестным владельцем, назначением, зависимостями или возможностью восстановления. Считать требующими сохранения до выяснения.

Срок или дата пересмотра — повод повторно оценить состояние с владельцем, а не команда удаления. Автоматического удаления по возрасту, категории, пути или квоте нет. Любая очистка требует отдельного согласования конкретных объектов, повторной проверки состояния и зависимостей непосредственно перед действием и сохранения нужных доказательств. Категория Regenerable не является разрешением на удаление.

## 6. Контроль соблюдения

До затратной операции агент фиксирует в манифесте: выбранное окружение и владельца, проверку конфликтов и независимости, совместимость сборки, оценку свободного места/пика/резерва и пути результатов. При неизвестных данных указывает `UNKNOWN` и останавливает зависимую операцию до выяснения. По завершении фиксирует результат, сохранённые доказательства, категорию хранения и следующего ответственного. Рецензент проверяет эти записи вместе с воспроизводимостью, а не считает наличие манифеста доказательством корректности.

При регулярном ручном обзоре активных задач ответственный сверяет владельцев, занятость, baseline, объём по томам и записи на пересмотр; согласованные частота и ответственный определяются командой. Неизвестные записи не очищаются. Можно подготовить read-only отчёт о неполных манифестах и объёмах; он не меняет данные и не утверждает безопасность очистки. Автоматическую проверку или интеграцию в CI рассматривать отдельно после согласования, без удаления, квот и блокирования существующих работ по умолчанию.

## 7. Подключение и поэтапное внедрение

1. Согласовать документ. Не менять действующие инструкции до отдельного разрешения. Затем **добавить**, сохранив все существующие изменения корневого `AGENTS.md`, одну строку: `Перед выбором worktree, сборкой или созданием артефактов прочитай и соблюдай docs/agent-workspace-storage-policy.md.` Эта явная команда нужна потому, что одна ссылка не гарантирует автоматическое чтение содержимого. Проверить применимые вложенные инструкции и отсутствие конфликтов.
2. **Codex:** корневой `AGENTS.md` — предлагаемый вход для запусков из соответствующей области проекта; проверить фактическую загрузку и ограничения конкретной среды. [Официальная документация Codex](https://developers.openai.com/codex/guides/agents-md/).
3. **OpenCode:** опубликованная документация описывает обнаружение `AGENTS.md` и дополнительный массив `instructions` в `opencode.json`/`opencode.jsonc`. Если проверка покажет, что корневая инструкция подхватывается, достаточно строки выше; альтернативно после согласования добавить `"docs/agent-workspace-storage-policy.md"` в существующий массив `instructions`, сохранив остальные поля. Учитывать `OPENCODE_DISABLE_PROJECT_CONFIG`, корень workspace и версию: путь, который не найден, может быть пропущен. На момент подготовки проектного `opencode.json`/`opencode.jsonc` в корне не обнаружено; создавать его заранее не требуется. [Документация OpenCode](https://opencode.ai/docs/instructions/).
4. **DeepSeek:** это может быть модель внутри Codex/OpenCode или отдельный клиент; универсальный автоматически читаемый `DEEPSEEK.md` не подтверждён. Установить фактически используемые клиент, версию и загрузчик инструкций; для Codex/OpenCode применить соответствующий путь выше, для иного клиента добавить явную инструкцию чтения в его поддерживаемую конфигурацию либо передавать документ в начале сессии. Не утверждать внедрение до проверки конкретного клиента. [Пример интеграции DeepSeek с Codex](https://api-docs.deepseek.com/quick_start/agent_integrations/codex/).
5. Проверить на новой безопасной задаче для каждого используемого клиента: агент действительно получил правило, называет политику и применяет выбор окружения, проверку места и манифест. Для уже работающих сессий передать инструкцию отдельно или применить изменения при следующем запуске, не прерывая задачу. Актуализировать указания после завершения дискового аудита Phase 2. Сам по себе этот документ не меняет сборки, CI или существующие worktree.
