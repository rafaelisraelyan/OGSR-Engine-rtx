## 2. Архитектура и ownership

```
DLL ogsr_physx_runtime.dll
├── PhysXContext (singleton, refcounted)
│   ├── PxFoundation        — один на процесс/DLL
│   ├── PxPhysics           — один на процесс/DLL
│   └── PxExtensions        — PxInitExtensions / PxCloseExtensions
├── RagdollRegistry (process-wide generations, capacity 4 scenes / 64 instances)
│   ├── SceneSlot 0..3  → PhysXRagdollScene*  (владеет backend)
│   └── InstanceSlot[]  → PhysXRagdollInstance* (владеет backend)
└── PhysXRagdollScene (на каждый SceneHandle)
    ├── PxDefaultCpuDispatcher (свой)
    ├── PxScene               (свой)
    ├── PxMaterial map        (scene-level, shared между instances)
    ├── StaticFragment map    (key → PxRigidStatic + PxTriangleMesh)
    ├── contact registry      (collisionInstanceId → PhysXRagdollInstance*)
    ├── stepIndex / accumulator / lastFrameId / lastResult
    └── PhysXRagdollInstance* (active list через registry)
```

**Правила владения:**

- `PxFoundation`/`PxPhysics` **не** создаются на ragdoll и **не** создаются на
  каждую сцену. `PhysXContext::acquire/release` держит refcount; последний
  `SceneDestroy` освобождает SDK-контекст.
- `PxScene`, dispatcher, материалы и static geometry принадлежат **сцене**.
- Actors, joints, bind hierarchy, pose state и diagnostics принадлежат
  **экземпляру**.
- `RagdollDestroy(A)` удаляет только actors/joints/contact tag A. Static
  geometry, scene, dispatcher, материалы и экземпляр B не затрагиваются.
- `SceneDestroy` сначала уничтожает все живые instances, затем scene-level
  ресурсы. Порядок зафиксирован в `RagdollRegistry::destroyScene` и
  `RagdollRegistry::shutdown`.
- `SceneDestroy` → `SceneCreate` не принимает старые handles: generation
  увеличивается, слот не переиспользуется со старым значением.

### SDK lifetime

`PhysXContext` намеренно создаётся через `new` и не удаляется статическим
деструктором: это исключает порядок разрушения между CRT DLL и PhysX при
`FreeLibrary`. `release()` освобождает `PxPhysics`/`PxFoundation`, сам объект
контекста остаётся пустым до конца жизни DLL.

## 3. Registry hooks: контракт и rollback

Внутренний контракт (публичный C ABI не менялся):

```cpp
struct RagdollInstanceCreateInfo
{
    OgsrPhysX2RagdollHandle handle;          // provisional, ещё не опубликован
    std::uint32_t collisionInstanceId;       // nonzero, уникален в процессе
    const OgsrPhysXRagdollDefinition* definition; // только на время вызова
    const OgsrPhysX2RagdollInstanceConfig* config; // только на время вызова
};

virtual bool createScene(const OgsrPhysX2SceneConfig&, void**, std::string*) = 0;
virtual bool createInstance(const RagdollSceneContext&, const RagdollInstanceCreateInfo&,
                            void**, std::string*) = 0;
```

- Backend **копирует** definition/config в собственные структуры
  (`convertDefinition`, `instanceConfig = *info.config`) и не сохраняет
  caller-owned указатели.
- Handle публикуется только после успешного `createInstance`. При ошибке
  generation и collision id считаются израсходованными, слот остаётся
  свободным, наружу возвращается нулевой handle.
- Partial construction: `PhysXRagdollInstance::initialize` при ошибке вызывает
  `destroy()` (joints → actors → contact tag) и только затем возвращает
  ошибку. `PhysXRagdollScene::createInstance` удаляет недоделанный instance.
- `destroyInstance` идемпотентен по `nullptr`; registry не вызывает hook
  повторно для уже retired слота.
- `shutdown()` и деструктор registry уничтожают instances → scenes → hooks.

Тест `testHookCreateInfo` проверяет: hook получает `sizeof(config)`,
`collisionInstanceId != 0`, совпадающий с опубликованным handle, ненулевые
`definition`/`config` и provisional handle, равный опубликованному.

## 4. C ABI v2

### Exports

DLL экспортирует **34** имени: 18 v1 + 16 v2.

```
OgsrPhysX2GetApiInfo
OgsrPhysX2SceneCreate / Destroy / IsAlive
OgsrPhysX2SceneSetStaticMesh / AddStaticFragment / Step
OgsrPhysX2RagdollCreate / Destroy / IsAlive
OgsrPhysX2RagdollGetPose / ApplyImpulse / ApplyCentralImpulse
OgsrPhysX2RagdollGetBodyMass / GetInfo / GetDiagnostics
```

`GetApiInfo` возвращает `structSize = 32`, magic, ABI 2.0,
`maxScenes = 4`, `maxInstancesPerScene = 64` и
`capabilityFlags = OGSR_PHYSX2_CAP_REQUIRED_P3_1` (биты 0–6):

| Capability | Реализовано | Доказательство |
|---|---|---|
| `CAP_SCENE` | да | `SceneCreate/Destroy/IsAlive`, две сцены в `test_v2_multi` |
| `CAP_MULTI_INSTANCE` | да | два 11/10 rig в одной сцене, full-rig contact, 2023 проверки |
| `CAP_INSTANCE_HANDLES` | да | generation-safe handles, stale rejection |
| `CAP_STATIC_FRAGMENTS` | да | `SceneAddStaticFragment`, транзакционная замена |
| `CAP_CONTACT_ATTRIBUTION` | да | contact A↔B, импульс на обоих instances |
| `CAP_FRAME_IDEMPOTENT_STEP` | да | повторный frameId → cached result |
| `CAP_PER_INSTANCE_DIAGNOSTICS` | да | независимые KE/energy/joint errors |

`OGSR_PHYSX2_CAP_CONFIGURABLE_WORKERS` **не** объявляется.

### Валидация

- Все handles проверяются registry до разыменования; stale/нулевые отклоняются.
- `structSize` проверяется для scene config, instance config, step result,
  `GetApiInfo`.
- Проверяются: finite floats, положительный timestep, диапазон `maxSubsteps`
  (1..16), solver iterations (1..64), `contactOffset > 0`,
  `0 <= restOffset < contactOffset`, флаги 0/1, `workerThreads <= 8`,
  `maxInstances <= 64`.
- Instance config: damping ≥ 0, density > 0, group/mask только из
  `RAGDOLL|STATIC`, group ≠ 0, group ≠ `STATIC` (static group зарезервирован
  за сценой), mask ≠ 0.
- Ragdoll definition: лимиты C ABI, null-указатели, enum-диапазоны, finite
  transforms/velocities/inertia, корректные shape/joint ranges.
- `GetPose` не публикует частичный результат: сначала проверяется
  `maxBodies >= bodyCount` и буфер, только потом заполняются поля.
- `GetBodyMass`/`GetInfo`/`GetDiagnostics` заполняют выход только при успехе.
- Нет process-global «current ragdoll»: каждый вызов идёт через handle →
  registry → backend.

`test_v2_abi` загружает **реальную** DLL и требует
`V2NegotiationStatus::Ready` при `requiredCapabilities =
OGSR_PHYSX2_CAP_REQUIRED_P3_1`; таблица указателей должна быть полной.
Негативная матрица loader-тестов (83 проверки) продолжает проходить.

## 5. Общая статическая геометрия

- `SceneSetStaticMesh` = фрагмент с ключом `0`.
- `SceneAddStaticFragment(key, …)` создаёт отдельный `PxRigidStatic` +
  cooked `PxTriangleMesh` и добавляет actor в сцену.
- Замена по существующему ключу **транзакционная**: сначала готовится новый
  fragment (validate → cook → actor → shape). Только после успеха старый actor
  удаляется из сцены и освобождается, новый добавляется.
- Ошибка cooking/валидации не трогает старую геометрию: тест подаёт
  `index = 99` при 4 вершинах, получает отказ и подтверждает, что
  `staticTriangles` и опора тел не изменились.
- Static actors не удаляются при `RagdollDestroy`; удаляются только в
  `SceneDestroy` (или при успешной замене фрагмента).
- Runtime eviction в P3.1-B отсутствует.
- Изменения запрещены во время `simulate/fetch` (`stepping` guard).
- Mesh cooking выполняется с двумя обмотками треугольников (двусторонняя
  коллизия); `staticTriangles` считает исходные треугольники.

Тест: два фрагмента `[-10,0]` и `[0,10]`, два ragdoll падают по разные стороны
границы, оба остаются на высоте `0.1 < y < 0.6` после 150 шагов.

## 6. Collision filtering (ADR §8.1)

`PxFilterData`:

- `word0` — collision group;
- `word1` — collision mask;
- `word2` — nonzero collision instance id;
- `word3` — flags (`FILTER_RAGDOLL`, `FILTER_STATIC`,
  `FILTER_DISABLE_SELF_COLLISION`).

Правило симметричное: `(word0_a & word1_b) != 0 && (word0_b & word1_a) != 0`.
Требуется ровно один classification flag; неизвестные/trigger пары
подавляются fail-safe. Глобальные mutable-флаги v1
(`g_suppressRagdollSelfCollision`, `g_collectRagdollContacts`) в v2 filter
shader не используются.

| Пара | Поведение |
|---|---|
| Тела одного ragdoll, self disabled | Suppress (одинаковый `word2` + флаг) |
| Тела одного ragdoll, self enabled | По group/mask |
| Два разных ragdoll | По group/mask (разные `word2`) |
| Ragdoll / static | По group/mask |
| Static / static | Suppress |
| Ragdoll / ODE | Вне сцены, coupling отсутствует |
| Trigger | Suppress |

### Контактный callback

`PxContactPairHeader::actors[0/1]` используется для атрибуции; указатели
`pair.shapes[i]->getActor()` **не** разыменовываются. PhysX 5.6.1 прямо
разрешает dangling shape/actor pointers в `TOUCH_LOST`; перед чтением
проверяются `PxContactPairHeaderFlag::eREMOVED_ACTOR_0/1` и
`PxContactPairFlag::eREMOVED_SHAPE_0/1`.

> Найденный дефект: первая версия callback вызывала `pair.shapes[0]->getActor()`
> и падала с AV на втором шаге при `TOUCH_LOST`-паре с удалённым shape.
> Исправлено переходом на `PxContactPairHeader::actors` + removal flags.
> Это зафиксировано в `artifacts/p31b-review/logs/` (первый прогон vs финальный).

Контактный импульс суммируется по `pair.contactImpulses`, penetration — по
`extractContacts`. Событие атрибутируется **обоим** instances, если оба
участвуют в паре.

## 7. Один scene-level fixed-step

`OgsrPhysX2SceneStep(scene, deltaSeconds, frameId, result, …)`:

- Fixed timestep **0.01 с**, gravity **(0, −19.62, 0)**, solver **16/4**,
  linear damping **0.05**, angular damping **0.2**.
- Один вызов обслуживает все активные instances сцены.
- Каждый физический шаг: `PxScene::simulate(0.01)` → `PxScene::fetchResults(true)`.
- Один `stepIndex` на сцену; `GetPose(A/B)` возвращает один и тот же
  `stepIndexLow/High`.
- Повторный `frameId` возвращает cached `OgsrPhysX2StepResult` без симуляции.
- Уменьшение `frameId` — ошибка.
- `delta == 0` не симулирует и не двигает `stepIndex`.
- `maxSubsteps` ограничивает число шагов за вызов; избыток учитывается в
  `droppedSteps`/`droppedSeconds`. `delta > 0.25` обрезается, остаток также
  попадает в dropped time.
- `GetPose`, `ApplyImpulse`, `GetDiagnostics` не вызывают `SceneStep`.
- Создание/удаление actors и static geometry при `stepping == true`
  отклоняется.

Проверено: 30 FPS → 3 шага, 60 FPS → 1 шаг, 120 FPS → 0 шагов
(накопление), `delta = 0.1` → 4 шага + dropped, повтор frameId → cached,
уменьшение frameId → отказ.

## 8. Lifecycle и безопасность

| Сценарий | Результат |
|---|---|
| Create A → Create B → simulate | PASS (11/10 + 11/10, общий stepIndex) |
| Destroy A → B продолжает | PASS |
| Create C в освобождённом слоте | PASS |
| Stale handle A → C | PASS (generation mismatch) |
| Повторный destroy A | PASS (отказ, без double-free) |
| SceneDestroy с A/B | PASS (оба invalid, старые handles отклонены) |
| SceneDestroy → SceneCreate | PASS (новые generations) |
| Partial failure создания B | PASS (A жив, B создаётся после) |
| Contact callback после destroy | PASS (contact registry очищен) |
| Registry shutdown | instances → scenes → hooks |
| DLL unload | loader обязан держать `V2ModuleLease`; registry деструктор чистит ресурсы |

**Обязательство для P3.1-C:** перед `SceneDestroy` игровой слой должен снять
bone callbacks и перестать читать pose; registry не знает об `IKinematics`.
Это задокументировано, игровой код не изменялся.

**Ограничение:** registry/backend не имеют внутреннего mutex. Контракт —
один поток-владелец на сцену; `SceneStep` не реентерабелен (`stepping` guard).
Это соответствует текущему игровому циклу и должно быть явно проверено при
интеграции.

### Контакт A↔B: упрощённый single-body тест

```
contact evidence: impulseA=2.4963 impulseB=2.4963 Bdx=0.9398
```

Сцена без гравитации, два single-body rig на расстоянии 0.6 м; к A применён

### Контакт A↔B: два полных 11/10 rig (P3.1-B-R1)

`testTwoFullRagdollsContact()` создаёт два полных P2.2A rig (11 bodies /
10 joints каждый) в одной `PxScene`, ставит их на расстоянии 1.2 м по X на
высоте 3 м и применяет к A центральный импульс `(60, 0, 0)` в body 5 (spine).
Массы, joints, damping, solver 16/4, gravity −19.62 и timestep 0.01 не
менялись.

```
full-rig setup: impulse=(60.0000,0.0000,0.0000) body=5 spawnA=(-1.2000,3.0000,0.0000)
                spawnB=(0.0000,3.0000,0.0000) B0=(0.0009,2.9944,0.0005)
full-rig pose B: initial=(0.0009,2.9944,0.0005) final=(0.2662,0.1344,0.3296)
                 maxBodyDisplacement=5.0088
full-rig contact evidence: frame=28 BminY=2.1221 Bx_contact=0.0476 Bx_final=0.2662
                           dB=5.0088 foundA=1 foundB=1 pairsA=1 pairsB=1
full-rig impulse evidence: frame=33 impA=7.8904 impB=7.8904 maxA=482.5128 maxB=668.8464
full-rig stability: anchorA=0.01140 anchorB=0.03231 limitA=0.10519 limitB=0.05536
                    KE_A=0.7266 KE_B=0.0000
full-rig B events: found=60 persist=4320 lost=51
```

Доказательство реального столкновения:

- первый контакт B — на frame 28, когда B ещё в воздухе (`BminY = 2.1221 м`),
  то есть единственный возможный партнёр — A;
- A и B одновременно сообщают `contactFound` и `activeContactPairs = 1`;
- на frame 33, пока B в воздухе, **оба** экземпляра получают одинаковый
  ненулевой контактный импульс **7.8904** — это одна и та же пара A↔B,
  атрибутированная обоим;
- B смещается по X с `0.0476` до `0.2662` (+0.2186 м) после контакта;
- все transforms обоих rig finite, `maxJointAnchorError` 0.0114/0.0323
  (порог v1 0.05), `maxJointLimitError` 0.1052/0.0554 (порог v1 0.2),
  KE finite;
- после `RagdollDestroy(A)` B продолжает симулироваться 60 шагов, его pose
  finite, `staticTriangles = 2`, сцена и static geometry живы.

`activeContactPairs` в v2 — **per-step** величина: число пар, приславших
`TOUCH_FOUND` или `TOUCH_PERSISTS` на последнем шаге. Это отличается от v1,
где счётчик кумулятивный (FOUND−LOST), и устраняет дрейф, если пара исчезает
без `TOUCH_LOST`.

### Потеря контакта и удаление экземпляра

`testContactLossOnDestroy()`:

```
contact-loss evidence: natural_lost=1 last_lost=0 active=0
destroy-contact evidence: lost=0 active=0
```

- При естественном разлёте двух тел приходит `TOUCH_LOST`
  (`natural_lost=1`), а `activeContactPairs` возвращается к 0.
- При удалении A, пока B ещё касается его, PhysX **не** присылает
  `TOUCH_LOST` (release вне `simulate`); контракт backend — не падать, не
  обращаться к удалённым shapes и не оставлять фантомных пар:
  `activeContactPairs = 0` на следующем шаге.
- Callback использует `PxContactPairHeader::actors` + removal flags и не
  разыменовывает `pair.shapes[i]`.

### Конфликт scene-level material IDs

`testMaterialConflictRejected()`: сцена уже создала material id 0 с
friction 0.8 (static floor). Попытка создать ragdoll с material id 0 и
friction 0.2 отклоняется с диагностикой `material id 0 is already used by the
scene with different parameters`; handle не публикуется, сцена жива. Rig с
совпадающими параметрами создаётся штатно. Это фиксирует ограничение
16-битного `materialId`: heterogeneous-rig интеграция обязана использовать
уникальные id или отдельный namespace.

### Static geometry failure

- Два фрагмента, два тела на разных сторонах границы — оба удерживаются.
- Замена с `index = 99` отклонена; `staticTriangles` остался `4`, тела
  продолжают опираться.
- Удаление A не освобождает static geometry и не влияет на B.

## 12. Известные ограничения и риски P3.1-C

1. **Один поток-владелец.** Нет mutex в registry/backend; параллельные вызовы
   из разных потоков не поддерживаются. Перед game integration нужен явный
   контракт (owner thread) или сериализация.
2. **`SceneDestroy` и bone callbacks.** Игровой слой обязан снять callbacks и
   прекратить чтение pose до destroy; иначе возможен доступ к освобождённым
   actors. Это требование к P3.1-C, не к backend.
3. **DLL unload.** Клиент обязан держать `V2ModuleLease` и уничтожить все
   scenes до `FreeLibrary`. Backend чистит ресурсы в деструкторе registry, но
   не может защитить от выгрузки во время активного вызова.
4. **Debug PhysX.** Полный Debug-прогон PhysX-зависимых тестов невозможен без
   debug-сборки PhysX SDK; Release покрывает физику.
5. **Static mesh cap.** 200k треугольников на фрагмент и 1M вершин — диагностический
   предел P3.1-B, не production-стриминг уровня.
6. **Hinge2 / сложные joint kinds.** `Hinge2` в P3.1-B возвращает ошибку
   (`not implemented`); поддержка ограничена теми kind, которые есть в
   P2.2A rig (Ball/Hinge/Euler3/Fixed/Slider).
7. **Материалы scene-level.** `materialId` — 16-битный ключ на сцену.
   Совпадающие параметры переиспользуются; конфликтующие параметры с тем же id
   теперь **отклоняются** при создании instance (`material id N is already used
   by the scene with different parameters`). Heterogeneous-rig интеграция
   обязана использовать уникальные id или отдельный namespace.
8. **Contact diagnostics.** В v2 `activeContactPairs` — per-step число пар,
   приславших `TOUCH_FOUND`/`TOUCH_PERSISTS` на последнем шаге, а не
   кумулятивный FOUND−LOST. v1 сохраняет старую кумулятивную семантику; не
   смешивать значения при сравнении.
9. **Производительность.** 8 rig ≈ 0.44 мс/шаг на этом стенде; бюджет для
   игрового кадра не согласован. При интеграции измерить на реальном уровне с
   большим static mesh и ODE-объектами.
10. **Independent review.** Этап не считается принятым до независимой проверки
    исходников и evidence.
11. **Extension lifetime v1 ↔ v2.** v1 (`PhysXRagdollWorld`) и v2
    (`PhysXContext`) независимо вызывают `PxInitExtensions`/`PxCloseExtensions`.
    Пока v2 не активирован в игре, это не проявляется. При P3.1-C нельзя
    закрывать extensions v1, пока живёт v2 (и наоборот): нужен общий
    refcount/lifetime на уровне процесса либо единый SDK-контекст. Требование
    зафиксировано в ADR (invariant 10) и должно быть закрыто до активации v2.
