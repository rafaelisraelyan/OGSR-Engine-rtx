## Зачем мы это делаем

OGSR RTX — это исследовательско-инженерная ветка **X-Ray / OGSR**, в которой мы переносим графическую основу *Call of Pripyat* с традиционного рендера **DirectX 11 / R4** на **нативный DirectX 12**, сохраняя работоспособный оригинальный путь как основу и способ отката.

Долгосрочная цель — **гибридный raster + DXR рендеринг**: аппаратные RT-тени, затем измеряемые отражения и непрямое освещение, современные материалы, объёмная атмосфера и устойчивая работа на больших открытых уровнях. *Control* и *Metro Exodus Enhanced Edition* — ориентиры для изучения подходов, **не готовые компоненты или скопированные технологии** этого проекта.

Проект не обещает «RTX в один клик». Мы последовательно решаем задачи форматов X-Ray, владения GPU-ресурсами, синхронизации, обхода сцены, кадрового цикла и регрессий игры.

### От пяти объектов — к карте Jupiter целиком

Наш ближайший визуальный рубеж — **не очередной набор отобранных кроватей, бочек и декораций**, а полная статическая локация, которую движок сам извлекает из оригинальных данных уровня:

```text
Оригинальные данные X-Ray (level / level.geom / visuals / DDS / THM)
                           │
                    R4 scene traversal
                           │
             immutable CPU scene snapshot
                           │
              GPU geometry + material registry
                           │
     DX12 command lists → queue/fences → swapchain → Present
                           │
                  Камера в настоящей игре
```

**F4.1** должен покрыть terrain, здания, дороги, статические конструкции, экземпляры и иерархии, честно учитывать неподдержанные декларации/материалы и исключить искусственные лимиты в штатном DX12-пути. На первом этапе достаточно *unlit/basic lighting*, корректных текстур, глубины и видимости — без обязательного DXR.

## Инженерные принципы

- **Game first.** Каждый крупный этап должен давать наблюдаемый результат непосредственно в игровом runtime, а не только в standalone тесте.
- **Безопасный rollback.** DX11/R4 и ODE не ломаются ради экспериментальных DX12 и PhysX путей.
- **Владение ресурсами доказуемо.** GPU fences, epochs/generations, immutable snapshots, retire/quarantine и GPU Debug Layer важнее красивого, но нестабильного кадра.
- **Автономная разработка с контролем.** Основной агент ведёт критическую интеграцию; помощники получают изолированные исследования, CPU-fixtures, проверки и документацию. Частые логические коммиты, адресные smoke-проверки, затем единая итоговая проверка и независимое ревью.
- **Evidence before PASS.** Логи, хеши кадров, артефакты, реальные игровые запуски и честные ограничения. `PASS WITH NOTES` не равен production merge.
- **Не прятать дефекты.** Открытые и исторические ошибки ведём в **[GitHub Issues](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues)**. Текущие расследования: [R4 startup AV #2](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/2), [DX12 shutdown AV #3](https://github.com/rafaelisraelyan/OGSR-Engine-rtx/issues/3).

## Сборка и запуск

**Для разработчиков:** Windows, MSVC с поддержкой C++20, Windows SDK и зависимости, перечисленные в [инструкции сборки](docs/03-build-and-dependencies.md). Основной файл решения — `Engine.sln`. Точные конфигурации, внешние SDK и игровой payload следует проверять по актуальным документам, а не предполагать по README.

```text
Engine.sln
├── ogsr_engine/       движок, игровой runtime, рендер, физика
├── Game/              игровые ресурсы и конфигурация
├── 3rd_party/         сторонние зависимости и SDK
└── docs/              архитектура, дорожная карта, evidence
```

> **Важно:** исходные игровые архивы, уровни и коммерческие материалы S.T.A.L.K.E.R. в экспериментальные отчёты и поставки DX12 не включаются. Нужна легальная установка соответствующей игры. README не является инструкцией для запуска пока не опубликованной DX12 feature-ветки.
